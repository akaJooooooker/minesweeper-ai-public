# 本機勝敗資料與候選策略實驗

日期：2026-09-06。模型參考為選定的 V44，GUI 顯示比例為 150%，格子基準 28，實際 42 像素。

## 問題與既有證據

一般自我遊玩紀錄早已用於訓練，不是新的資料來源。`replays-on-policy-train-v14-a/b.jsonl` 共 2,000 局（937 勝、1,063 敗），全部是高級 30×16／99 雷。`v39-agent-train-a/b/c/d.jsonl` 有 1,784 個高級候選格比較局面，其中 339 個有不同候選勝敗；沒有本次 GUI 的地獄 30×20／130 雷。

V33 曾用整局勝敗調整每個猜測動作，實際配對勝率退步；V38、V39 增加候選格比較資料也沒有直接提高配對勝率。詳見同目錄 `replay-agent-v33-v34.md`、`replay-agent-v35-v39.md`。不能假設繼續累積一般敗局，就必然提高模型勝率。

## 操作層修正

`LiveDecisionEngine` 原本在沒有確定安全格時，重新以 `analysis.probabilities` 排序，覆蓋 `HybridAgent` 已結合神經網路風險與結果策略的選格。現在只要模型選擇的格子可點擊，就保留該決策、理由與雷率；限制區域仍生效，確定安全的展開與連開仍優先。另加入矛盾盤面不可猜測的防護。

此為 GUI／桌面外掛的銜接修正，不是 V44 權重更新。成對測試的兩個模型都使用修正後的操作層，因此候選與參考之差只反映新的策略權重，不能用來宣稱操作層修正提高了多少勝率。

## 新資料

使用 `local_selfplay.py`，相同 V44 設定、公開盤面輸入、純無旗，首點展開空白區。這與舊正式 standard 測試的「首點只保證安全」不同，勝率不可直接比較。4 程序、每程序 1 個 PyTorch 執行緒。

96 局流程試跑後，正式收集高級／地獄各 1,000 局，耗時 255.13 秒。原始紀錄位於 `data/selfplay-v44-batch1/episodes/`，全部勝敗都保留。

## 品質與分組

所有 2,000 局都以真實雷位和操作順序重新播放，勝敗一致。訓練／驗證在開局前依序號固定分組，盤面雜湊沒有交集。每局最多記錄 2 個非精確猜測局面，每局面比較 3 個低風險候選，以相同 GUI 決策引擎完成各個分支。

194 個局面分為訓練 158（28 個候選勝敗不同）、驗證 36（6 個候選勝敗不同）。每個原選格的分支結果，都與原對局勝敗相同。訓練使用全部局面，包含所有候選都勝或都敗的局面，以保留校準訊號；8 種幾何變換後共有 1,264 筆訓練例。資料沒有提供真實雷位給模型。

候選的單盤 0／1 結果是模擬樣本，不是已知的一般勝率；這批有區分力的局面仍少。

## 候選訓練

輸出 `models/replay-agent-local-selfplay-candidate.pt`。只調整 `standard_policy_head` 的 reveal 通道；逐張量驗證 Risk、Value、骨幹及其他動作通道均與 V44 相同。原 V44 checkpoint 的 SHA-256 仍為 `f8f827afa6c3a67d0b5909978b2f285d8430babdcc1f8e274f2b8ae391851fd4`。

學習率 0.0001、batch 64、ranking／BCE 權重各 1、最多 40 epochs、patience 8。以 RTX 4070 Ti SUPER 執行，PyTorch 記憶體上限為 GPU 的 50%。訓練在第 26 epoch 停止，保留第 18 epoch。

驗證 Brier 由 0.258125 降至 0.253169；選中勝利分支仍為 13／36（36.11%），沒有提升。不能只憑較低的離線誤差宣稱模型更強。

## 獨立配對測試

訓練開始前固定測試種子 `175985001720591491`，高級／地獄各 2,500 張新棋盤，共 5,000 對。每對兩個模型收到同一棋盤，使用首點空白區與純無旗，並交替先後順序降低計時順序偏差。8 程序，每程序 1 個 PyTorch 執行緒；測試盤沒有加入訓練或調參。

事先設定的門檻：合計勝局提高且精確 McNemar p < 0.05，各難度不能退步超過 0.5 個百分點。完整設定見 `local-selfplay-20260906-protocol.json`，完整結果見 `local-selfplay-20260906-result.json`。


### 執行中斷與恢復

首輪配對測試在保存 2,520 個完整配對後遇到 `SystemError: Invalid format string ($ before |)`，Python 3.12.14 的 traceback 指向求解器鄰居迴圈內的內建 `min` 呼叫；目前沒有確認底層根因。此例外沒有被計為敗局。

比較工具補上 `--resume`：核對模型／設定與棋盤種子、保留已完成配對、只補跑缺少的序號、拒絕重複或不完整紀錄。單一程序例外會獨立保存，並在新程序重試一次；仍失敗就明確保留測試未完成，不能套用模型升級門檻。此次接續的種子、棋盤數、兩個模型、推理程式與升級門檻均未改動。

**候選未升級，正式 GUI 繼續使用原 V44。** 額外 2 勝不足以通過事先固定的門檻。這次資料與訓練流程可行，但沒有證明新策略提高了勝率，也不能據此斷言模型永遠不需要更多資料。

第二次 8 程序執行有工作程序非正常結束，使 882 個進行中／待執行配對收到 `BrokenProcessPool`；這不是 882 次獨立崩潰。工具保留已成功的結果，再以 4 個新程序補完這 882 個配對，沒有再留下未完成項。最終 5,000 個配對全部唯一、勝敗完整，與收集批次的種子無重疊；兩個 checkpoint 的雜湊仍一致。8 程序的底層錯誤根因仍未確認，因此後續工具預設 4 程序，不變更系統或 Python 安裝。

一般勝敗資料值得保留，但本次更有針對性的缺口是地獄盤、模型真正介入時的候選選擇。新批次只有 34 個能區分候選勝敗的局面，不能把 2,000 局或 1,264 筆變換樣本當作等量的獨立關鍵決策。後續如再擴大，應保留勝敗兩類、集中增加不同棋盤的困難候選比較，並另設新測試；不將本次 5,000 張測試盤回填訓練。

## GUI 與驗證

150% 的視窗已開啟，標題為「本機踩地雷 · V44 · 150%」。格子基準 28、實際 42 像素；整個地獄盤完整可見。長按只加深未揭露且未插旗的格子，新局按鈕在套用自訂旁。

完整測試 126 項通過；其後新增的續跑紀錄驗證也通過，成對工具的 3 項測試確認相同模型結果一致、種子與收集分離、拒絕重複／不完整配對。自動保存與多程序模擬本身不會啟動訓練；本次候選訓練是使用者提出統整勝敗模擬後，另行執行的獨立實驗。
